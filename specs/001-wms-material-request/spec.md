# คุณลักษณะ: ระบบร้องขอวัสดุและจัดส่ง (WMS Material Request & Dispatch)

**Feature Branch**: `001-wms-material-request`  
**วันที่สร้าง**: 2024-??-??  
**สถานะ**: ฉบับร่าง  
**อินพุต**: ขอบเขตจากผู้ใช้เกี่ยวกับการร้องขอวัสดุ, การจัดเก็บ, การสแกน QR และการจัดรอบการส่ง

## สถานการณ์ผู้ใช้ & การทดสอบ

### User Story 1 - ขอวัสดุผ่านแคตตาล็อก (Priority: P1)

ผู้ใช้หน้างานค้นหาวัสดุผ่านหน้าจอแบบ e-commerce (คล้าย Shopee) เลือกหมวดหมู่ เห็นสต็อกคงเหลือ เพิ่มของลงตะกร้า กำหนดวันที่ต้องใช้ และส่งคำร้อง (Request) ไปยังคลัง

**เหตุผลความสำคัญ**: เป็นจุดเริ่มของกระบวนการทั้งหมด หากส่งคำร้องไม่ได้ ระบบส่วนอื่นไม่เกิดคุณค่า

**การทดสอบแบบอิสระ**: ทดสอบด้วยการสร้างผู้ใช้บทบาท requester เปิดแคตตาล็อก, ใส่สินค้าหลายรายการ, กำหนดวันส่ง และยืนยันว่า request ถูกบันทึกใน Firebase พร้อมไฟล์แนบใน Cloudflare R2

**Acceptance Scenarios**:

1. **Given** ผู้ใช้ล็อกอินและมีสิทธิ์ requester, **When** ค้นหาวัสดุในหมวดที่ต้องการและเพิ่มลงตะกร้า, **Then** ระบบแสดงยอดคงเหลือแบบเรียลไทม์และจำนวนในตะกร้าถูกอัปเดต
2. **Given** ผู้ใช้เตรียมตะกร้าและระบุวันที่ต้องการ, **When** กดส่งคำร้อง, **Then** ระบบสร้างเอกสาร request พร้อมรายการ, สถานะเริ่มต้น `pending_review`, และแจ้งเตือนหน่วยงานคลัง

---

### User Story 2 - พนักงานคลังรับคำร้องและจัดเตรียม (Priority: P1)

เจ้าหน้าที่คลังเปิดหน้าจอ Store Ops เห็นรายการคำร้องที่รอหยิบ พร้อมข้อมูล Location ที่ต้องไปหยิบสำหรับแต่ละ item และสถานะสินค้า

**เหตุผลความสำคัญ**: ทำให้คลังวางแผนงานและจัดเตรียมสินค้าได้ตรงเวลา ลดการล่าช้า

**การทดสอบแบบอิสระ**: ทดสอบด้วยการมี request ที่ได้รับการอนุมัติแล้ว ระบบต้องแสดงรายการที่ต้องหยิบพร้อม location/bin ที่เชื่อมโยงจากข้อมูล master

**Acceptance Scenarios**:

1. **Given** มี request ที่สถานะ `approved`, **When** เจ้าหน้าที่เปิดหน้าจอ Store Ops, **Then** ระบบจัดกลุ่มรายการตาม priority/due date พร้อมแผนผังตำแหน่งจัดเก็บ
2. **Given** เจ้าหน้าที่ต้องการดูรายละเอียดสินค้า, **When** คลิกที่รายการ, **Then** ระบบแสดงข้อมูล lot/serial, สถานะสต็อก และหมายเหตุพิเศษ (เช่น ต้อง QC)

---

### User Story 3 - สแกน QR เพื่อรับเข้า/ตัดสต็อก (Priority: P2)

เจ้าหน้าที่ใช้มือถือสแกน QR ที่ติดอยู่บน Location หรือสินค้าชุดนั้นเพื่อทำ put-away หรือ picking โดยระบบอัปเดตสต็อกอัตโนมัติ

**เหตุผลความสำคัญ**: ลดข้อผิดพลาดจากการกรอกมือ และสร้าง audit trail ที่ตรวจสอบย้อนหลังได้

**การทดสอบแบบอิสระ**: ทดสอบผ่านอุปกรณ์มือถือ เปิดหน้า UI โหมดสแกน เลือกประเภท transaction (รับเข้า/หยิบออก), สแกน Location + Item, ปรับจำนวน และบันทึกสต็อก

**Acceptance Scenarios**:

1. **Given** เจ้าหน้าที่อยู่ในโหมด Put-away, **When** สแกน QR Location และสินค้า, **Then** ระบบเพิ่มจำนวนสต็อกใน Location นั้นและบันทึกผู้ทำรายการ
2. **Given** เจ้าหน้าที่อยู่ในโหมด Picking, **When** สแกน Location แล้วเลือกคำร้องที่ต้องหยิบ, **Then** ระบบหักสต็อกและเชื่อมกับ Request Line ที่เกี่ยวข้อง

---

### User Story 4 - จัดรอบส่งและใบงาน (Priority: P3)

หัวหน้าขนส่งรวมคำร้องที่อนุมัติแล้วเป็นใบงานประจำสัปดาห์ กำหนดรถ, ผู้ขับ, วัน-เวลา ส่งออกเป็น checklist ให้ทีมโหลดของ

**เหตุผลความสำคัญ**: ช่วยให้การจัดส่งเป็นระบบ มีหลักฐานว่าอะไรต้องขึ้นรถคันไหนและสถานะการส่งมอบ

**การทดสอบแบบอิสระ**: ทดสอบด้วยการเลือกคำร้องหลายรายการ สร้าง work order, ระบุ vehicle และ schedule, อัปเดตสถานะจาก `planned` → `loaded` → `delivered`

**Acceptance Scenarios**:

1. **Given** มี request ที่พร้อมส่งหลายรายการ, **When** หัวหน้าขนส่งสร้างใบงานใหม่, **Then** ระบบรวมรายการตามเส้นทาง/รถที่เลือกและกำหนดรอบเวลา
2. **Given** ทีมโหลดของทำงานตามใบงาน, **When** บันทึกสถานะการโหลดและยืนยันส่งมอบ, **Then** คำร้องย่อยแต่ละรายการถูกอัปเดตสถานะและบันทึก timestamp

---

### กรณีชายขอบ (Edge Cases)

- หากสต็อกไม่พอเมื่อผู้ใช้กดส่งคำร้อง ระบบต้องแจ้งเตือนทันทีและให้ผู้ใช้เลือกลดจำนวนหรือส่งคำร้องไว้ในคิว backorder
- หาก Location ถูกสแกนแต่ไม่ตรงกับสินค้าที่อยู่ในคำร้อง ระบบต้องบล็อกการหักสต็อกและแจ้งเตือนเพื่อป้องกันการหยิบผิดสินค้า
- หากสัญญาณอินเทอร์เน็ตอ่อนในพื้นที่สแกน ระบบต้องบันทึกธุรกรรมแบบ offline queue แล้วซิงก์เมื่อกลับมาออนไลน์

## ข้อกำหนด

### ข้อกำหนดเชิงฟังก์ชัน (Functional Requirements)

- **FR-001**: ระบบต้องให้ผู้ใช้งานค้นหาและเรียกดูแคตตาล็อกวัสดุพร้อมหมวดหมู่และจำนวนคงเหลือแบบเรียลไทม์จาก Firebase
- **FR-002**: ระบบต้องให้ผู้ใช้สร้าง ตะกร้า และส่งคำร้อง พร้อมแนบไฟล์ (เช่น รูปแบบการใช้) ไปยัง Cloudflare R2
- **FR-003**: ระบบต้องให้เจ้าหน้าที่คลังเห็นคิวคำร้องที่อนุมัติแล้ว พร้อมข้อมูล Location, Lot/Serial และสถานะหยิบ
- **FR-004**: ระบบต้องรองรับการสแกน QR Location/Item เพื่อทำธุรกรรมรับเข้า-จ่ายออก โดยบันทึกจำนวน, หน่วย, ผู้ทำรายการ และ timestamp
- **FR-005**: ระบบต้องเก็บประวัติ stock movement และสร้าง audit trail สำหรับการตรวจสอบย้อนหลัง
- **FR-006**: ระบบต้องสร้างใบงานการจัดส่ง ประกอบด้วยรถ, คนขับ, เส้นทาง, คำร้องที่รวมในเที่ยว และสถานะการโหลด/ส่งมอบ
- **FR-007**: ระบบต้องจัดการสิทธิ์การใช้งานตามบทบาท (Requester, Store Clerk, Logistics Lead, Admin)
- **FR-008**: ระบบต้องมี API/เว็บฮุคสำหรับแจ้งเตือนสถานะคำร้อง (เช่น Slack/Email) [ต้องยืนยันช่องทางจริง]
- **FR-009**: ระบบต้องรองรับการปรับจำนวนสต็อกด้วยเหตุผลพิเศษ (เช่น นับรอบ, ชำรุด) โดยแยกประเภท adjustment ชัดเจน

### เอนทิตีสำคัญ (Key Entities)

- **Item**: SKU, ชื่อ, หมวดหมู่, หน่วย, รูปภาพ (URL จาก R2), สถานะเปิดใช้งาน
- **Category**: รหัสหมวด, ชื่อ, ลำดับการแสดง, พาเรนต์ (รองรับหลายระดับ)
- **InventoryLocation**: โซน/แถว/ช่อง, ประเภทพื้นที่ (Pick/Reserve), QR code token, ความจุสูงสุด
- **InventoryBalance**: Location, Item, Lot/Serial, ปริมาณคงเหลือ, ปริมาณค้างหยิบ
- **Request**: รหัสคำร้อง, ผู้ขอ, หน่วยงาน, วันที่ต้องใช้, สถานะ (pending, approved, picking, loaded, delivered, cancelled), หมายเหตุ
- **RequestLine**: อ้างถึง Request, Item, จำนวนที่ต้องการ, จำนวนอนุมัติ, จำนวนหยิบจริง, สถานะย่อย
- **WorkOrder**: รหัสใบงาน, ช่วงเวลา, รถ, คนขับ, เส้นทาง, สถานะ (`planned`, `loading`, `in_transit`, `completed`, `cancelled`)
- **WorkOrderTask**: ผูกกับ WorkOrder และ RequestLine, ลำดับงาน, สถานะปัจจุบัน
- **StockMovement**: ประเภทธุรกรรม (put-away, pick, adjustment), Location, Item, จำนวน, ผู้ทำรายการ, แหล่งอ้างอิง (RequestLine/WorkOrder)

## เกณฑ์ความสำเร็จ (Success Criteria)

### ตัวชี้วัดที่วัดได้

- **SC-001**: ผู้ใช้ requester 90% สามารถค้นหาและส่งคำร้องเสร็จภายใน 3 นาทีในรอบทดลอง
- **SC-002**: คำร้องที่อนุมัติแล้วสามารถระบุ Location ที่ต้องหยิบได้ครบถ้วน 100% ก่อนเริ่มหยิบของ
- **SC-003**: เวลาจากเริ่มหยิบถึงยืนยันหยิบสำเร็จลดลงอย่างน้อย 30% เมื่อเทียบกับกระบวนการกรอกมือเดิม
- **SC-004**: ใบงานส่งของสัปดาห์หนึ่งต้องมีสถานะ `completed` ไม่น้อยกว่า 95% ภายใน SLA ที่กำหนด
- **SC-005**: ทุกธุรกรรมสแกน QR ต้องถูกบันทึกพร้อม timestamp และผู้ปฏิบัติงาน 100% เพื่อรองรับการ audit
